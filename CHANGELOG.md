# Changelog

## 1.10.0 - 2026-08-04

- Closed 24 defects found by probing the tree adversarially rather than by waiting for a report, each one reproduced before it was written and each carrying a test observed failing against the unfixed source. They fall into four classes, and every class turned out to have several instances, which is the part worth recording: a defect that appears once is a mistake, and a defect that appears four times is a decision that was made in four places.
One decision, several implementations. Four modules under `skills/solve-efficiently/scripts/` each reimplemented the tokenizer `scripts/skill_routing.py` already owns, and each got it wrong differently -- `semantic_provider` matched by substring with no stopwords and selected 3,537 of this repository's 3,801 graph nodes for one prompt; `memory_context` returned records sharing only "the"; `context_pipeline` counted substrings uncapped, so a 2,480-character README sharing no content word scored 281 against the relevant file's 6 and took the whole character budget; `context_lens` returned `CHANGELOG.md` and nothing else. The ownership rule that keeps two work packets off one file lived in three modules that had already drifted, and all three read `src /a.py`, `src./a.py` and `src/a.py:stream` as different files from `src/a.py` -- spellings Windows resolves onto one file.
Untrusted numbers taken at their word. The browser, desktop and design evidence gates coerced provider counters with `int()`, so `"many"` and `null` raised out of the gate while `"1"`, `1.9`, `true` and an absent failure count were accepted as proof; `communication_contract` read with `float()` the same `qualityScore` field `work_state` validates strictly; and `context7_lookup` let ranking scores escape as `ValueError` and `TypeError` past `main()`'s except tuple, with `nan` quietly deciding the winner.
Fail-open freshness. `probe_codegraph` skipped any counter that was not already an `int`, so a status stating two modified files as a string reported a clean, usable index, and every unrecognised shape resolved the same way. The graphify detector dropped entries it could not read, which removes them from the pending set, so a changed file spelled as an object made the index report complete. The `Stop` completion gate answered an emptied ledger with the silence it owes a session that changed nothing -- and only an edit-tool event ever creates that file, so an empty one is a ledger whose content was lost.
Domain errors escaping as tracebacks. `UnicodeDecodeError` is a `ValueError`, so six readers of externally written files crashed on anything not UTF-8, a guard `skyvern_evidence` already carried with the reasoning written above it. Two more belong to no class: native memory undo restored a snapshot without checking it against the `before_sha256` its own receipt recorded, so a corrupted snapshot overwrote the live store and was reported as success; and capability overlap used Jaccard over descriptions 33 to 81 terms long against candidate summaries of six to ten, which caps a perfect subset below the 0.24 it is compared against, so containment restores the threshold the numbers were calibrated for.

- Refused a zero-width confidence interval where one observation is all there is. `_bootstrap_interval` and `_stratified_fixture_interval` returned `[v, v]` for a single value, and the caller reads exactly `ci[0] > 0`, so a width of zero cleared the confidence gate rather than failing it: twelve pairs of one fixture satisfy `minimum_live_pairs`, which counts pairs and not fixtures, and a quality delta of 0.0001 then passed as readily as 0.5. `None` is what both functions already return for "nothing to bound" and what the caller already handles, so `proven` now falls back to its own stated reason instead of resting on a certainty nobody measured.

- Gave both hook manifests one answer to which tools are writes. The manifests carried three different matcher sets between them: the Claude guard entry omitted `NotebookEdit` while the ledger entry beside it matched it, and the Codex manifest omitted both it and `MultiEdit`. A matcher naming too few tools raises nothing and logs nothing -- it produces an event that is simply never recorded -- so the only visible symptom would have been a completion gate that stayed quiet about an edit it never saw. The existing guard pinned one entry of one manifest, which is why the drift returned twice beside it; `test_both_manifests_agree_on_which_tools_are_writes` now holds every `PostToolUse` entry of both manifests to one set, differing only by each host's own tool vocabulary.

- Made the completion gate satisfiable on a host whose session working directory encloses the data root, where it had become the exact inverse of the defect it was fixed from. `_event_cwd` was corrected so that a session opened at a drive root or the home directory keeps recording provenance, on the ground that the gate was otherwise silently inert there; the ledger has been written correctly ever since, and every remediation it printed was impossible to follow. `work_state.py` refuses a workspace containing its own evidence store, in `session_directory` and again in `source_fingerprint`, so the durable session could not be rooted at that working directory -- and `record-validation` required the workspace to *contain* the recorded `cwd`, so it could not be rooted anywhere else either. There is no third choice: every root that contains such a cwd also contains the store, and every root that avoids the store fails to contain the cwd. Two halves enforcing opposite rules about one relationship is not strictness, it is an unsatisfiable gate, and this one fired every turn, printed three steps, and then refused the receipt those steps produce with `evidence belongs to a different workspace` -- a message that reads as a mistyped `--session-id` rather than as a configuration the instructions cannot be followed in. Both 1.9.x states leave the same host with no working verification path; the gate has only stopped being quiet about it.

The receipt check now asks that the durable session and the recorded edit share one tree in either direction, and that concedes nothing the old rule was holding. A receipt binds to the latest event's `eventHash` and never to a file -- `test_an_outside_cwd_edit_arms_a_gate_a_receipt_still_clears` already pins that -- so a workspace enclosing `cwd` was never evidence that the receipt was about the edit, and rooting a session at an ancestor and running any green command satisfied the old rule just as cheaply as rooting it at a subdirectory satisfies this one. What both directions do establish is that the two are not unrelated trees, which is the whole of what the check ever proved, and a receipt from an unrelated tree is still refused -- now naming both directories, because a refusal an operator cannot locate is one they read as their own mistake.

Excluding the data root from `source_fingerprint` instead was the tidier-looking fix and was measured before being rejected: the walk already skips `.cognitive-powers` and `.codegraph*`, so adding the store looks like one more entry in the same list. It does not produce a working path. `os.walk` over one real home directory enumerated 232,693 files and raised 188 `PermissionError`s, the first at `AppData\Local\Application Data`, and `source_fingerprint` re-raises the first `OSError` its `onerror` handler sees. Dropping the containment rule would have moved the refusal from `durable data root must be outside the workspace` to `cannot enumerate workspace source` and called it fixed.

The warning names the configuration now instead of leaving it to be discovered: when the data root sits inside the session's working directory it prints both paths, points at the subdirectory route and at `COGNITIVE_POWERS_DATA`, and says to prefer a subdirectory the host does not write to continuously -- the fingerprint covers the whole workspace, so a tree under continuous host writes goes stale between `run` and `verify`, which is what the subdirectory workaround runs into first. `docs/operations.md` gains that as a fifth property of the gate, and states what the two-identity rule can and cannot enforce: it compares two strings, so what it checks is that two names were given, and what it is for is a second party that did not produce the result.

- Moved the post-publication record into the job that verifies the release, deleting the one release step no gate could ever watch. It ran last, after every gate had finished, on a release that was already out, and it failed the way that shape of step always eventually fails: `v1.9.1` was published and never entered `docs/releases.json`, which is the sole source of the documented rollback target, so the next bump would have sent a reader escaping a bad release straight past the release in between. The checklist was not the problem. A step whose only enforcement is that someone remembers it is unenforced, and this repository has now recorded that same shape three times -- a rule stated in prose with no gate behind it. `record-published-release` runs after `verify-published-assets` and only on its success, so the entry is bound to the run that reproduced the archive byte-for-byte from the tagged source and verified its provenance: the record cannot exist without the evidence for it, and a release that failed verification keeps being one `docs/releases.json` refuses to claim.

- Retired the `DRY_RUN_RELEASE_REF` repository variable rather than automating it, because `GITHUB_TOKEN` cannot write Actions variables and the alternative was a personal access token held for one line of bookkeeping. The nightly dry run now reads the newest entry of `docs/releases.json` -- the file the publisher itself writes -- so the value it exercises and the value the release produced are the same value rather than two carriers hoping to agree. They had already stopped agreeing: the variable still named `v1.9.0` after `v1.9.1` shipped, so the nightly run kept installing a superseded release and reported green about it, which is the failure mode a dry run exists to make impossible. Two carriers maintained by hand drift; one carrier written by a gate does not.

The delegation contract was already complete — `orchestration_policy.py` selects a mode, assigns ownership, reserves the verifier slot and holds depth one; `agent-roles.md` states what each role owes — and none of it named a role the host could be addressed by. The three missing roles are the sharper half. `AGENT_ROLES` has admitted `investigator`, `researcher` and `reviewer` since the planner was written, and `READ_ONLY_ROLES` is those three exactly — they are the only roles it will place at depth two, and a unit declaring one of them validates, plans, and returns an assignment. `agents/` shipped none of them, so that assignment resolved to a general worker on every host, and the read-only property the planner had just enforced in the plan was enforced nowhere in what ran. It now spawns the registered verifier without the expected verdict, and gives each review angle its own reviewer instead of running the angles as successive passes over one context, where the second pass inherits the first's blind spot along with its conclusion. Where a host registers no role — Codex registers none from the plugin root — the fallback is unchanged and must be recorded as what it is: the contracts still apply, but only as description, and a durable criterion must not close as though the verdict had an independent source when it did not.
No activation measurement accompanies this. `evals/` can say whether a workflow fires; nothing here can yet say whether a fired workflow addresses the registered role rather than a general worker, and that is the claim the change actually makes. Treating the tool sets as the evidence is legitimate only for what a tool set can prove — that a spawned `reviewer` cannot write, that no role can spawn a descendant — and not for how often the right role is spawned at all.

Claude Code writes one transcript row per content block and repeats the identical usage on each, so usage is counted once per message id; summing rows would multiply a single message's cost.
